claim: Both output adapters install `this.socket.on('error', () => {})` — a total swallow — and gate every send on a private `ready` flag that is only set inside the bind callback. A bind failure (stale `iface` address after the drummer switches ethernet→wifi, EADDRNOTAVAIL, EACCES, EADDRINUSE on the sACN reuseAddr socket) emits 'error', the bind callback never fires, `ready` stays false, and `send()` returns early forever. Every subsequent per-send error is likewise dropped by the `() => {}` completion callback. The result is a completely dark rig with the UI happily reporting frames-per-second and packets-out, and nothing in the Monitor stream, the console, or the #122 telemetry pipeline saying why. This is exactly the failure OSC input was fixed for in commit d1d6eb9 ('surface socket errors') — `OscInput` now has a first-class `OscInputStatus` seam with a latched `state: 'listening' | 'error'`, an error code, and `onStatus` subscription. The product's actual OUTPUT path never got the same treatment, so the asymmetry is a known-correct pattern that simply was not applied where it matters most.
