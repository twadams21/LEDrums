claim: `resolvePin` mints a 6-digit numeric PIN (10^6 space) whenever the Cloudflare tunnel is enabled, and that PIN is the ONLY thing standing between the public internet and full authoring control of the rig. The connection handler simply calls `admitDecision` and, on refusal, `ws.close(4401)` — there is no attempt counter, no per-IP backoff, no lockout, and no monitor event on repeated refusals, so an attacker can dial the tunnel endpoint as fast as it will accept connections until the PIN falls. The legitimate client pauses its reconnect loop on 4401, but that is client-side courtesy, not a server control. Secondarily, `check()` compares with `supplied === pin` while the host token in the very same file correctly uses `safeEqual`/`timingSafeEqual` — the weaker credential got the weaker comparison. There is also no audit trail: nothing distinguishes 'nobody connected' from 'ten thousand refused attempts last night'.
