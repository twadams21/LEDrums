claim: Patch node identity is a stringly-typed grammar `<kind>:<a>[:<b>]` (patch-topology.ts:110) with builders scattered across three modules, and the `output:` prefix is claimed by TWO builders with different payload semantics. `patch-topology.ts:117` builds `output:${index}` from a POSITIONAL index (used at line 217), while `patch-graph.ts:66` builds `OUTPUT_PREFIX + outputId` from an `OutputConfig.id` for round-trip decoding by `parseOutputNodeId` (line 71). Nothing distinguishes the two at the type level or at runtime: `parseOutputNodeId('output:0')` produced by the topology builder returns `"0"` as if it were a config id, and conversely `describePatchNode` (patch-topology.ts:282-283) renders any output node's payload as the human-facing number — so a v2 output node keyed by its config id displays a raw id where the operator expects "Output 2". The same duplication exists for other kinds: `drumNodeId` (patch-topology.ts:115) and `drumZoneId` (patch-zones.ts:48) are two independent definitions of the identical string, as are `triggerId` (topology:113) and `triggerNodeId` (zones:50). `describePatchNode`'s `default:` arm (line 285) then classifies any unrecognised prefix as stage `'input'` rather than erroring, so a mismatched encoding surfaces as a wrongly-staged node, never as a failure.
