claim: `statsTimer` fires every 10ms and calls `broadcastJson`, which serializes a full stats object (including per-voice arrays under voice mode) and pushes it to every OPEN socket. `broadcastJson` never consults `ws.bufferedAmount` — a grep for `bufferedAmount` across apps/server/src and apps/web/src returns nothing. A remote viewer over the Cloudflare tunnel on a phone, or any peer whose TCP window collapses, cannot drain 100 messages/second; `ws` buffers the undeliverable frames in the Node process, and the queue grows for as long as the socket stays technically OPEN — which, per the heartbeat finding, is forever on a half-open link. Compounding it, `clients.admit(ws)` enforces no maximum connection count, so a shared room link (or a script against a 6-digit PIN) multiplies the per-client 100 Hz stream without limit. The machine under attack is the one driving a live show.

evidence the author gave:

  [read]  :: apps/server/src/main.ts:493 — `clients.admit(ws);` with the comment 'Admit additively (no eviction)'. No cap.

proposed fix: In `broadcastJson` (and `relayToOthers`), skip any socket whose `bufferedAmount` exceeds a threshold (e.g. 1MB) and count the skip; when a socket stays over the threshold across N consecutive sweeps, `terminate()` it and emit an error Monitor event naming the peer. Independently, drop the stats cadence from 100 Hz to something a UI can actually render (the preview stream is already throttled to 30fps) and add a `LEDRUMS_MAX_CLIENTS` cap enforced in the connection handler, refusing beyond it with a distinct close code.
