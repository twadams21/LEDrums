claim: `void data.arrayBuffer().then((buf) => this.cb.onFrame?.(new Uint8Array(buf)));` has no `.catch`. Two ways this rejects: `Blob.arrayBuffer()` itself can reject (the browser may have discarded the backing store under memory pressure), and — more likely — a throw inside the `onFrame` callback propagates into the promise chain instead of the synchronous path, where the ArrayBuffer branch two lines above would have surfaced it normally. The result is an `unhandledrejection` on a hot per-frame path, which under the #122 web-error capture becomes a flood of shipped error reports for something the code was clearly written to shrug off. It is also a silent behaviour asymmetry: the same frame delivered as an ArrayBuffer, a Uint8Array, or a Blob takes three different error paths.

evidence the author gave:
  [read]  :: apps/web/src/lib/ws/client.ts:220-232 — the ArrayBuffer and Uint8Array branches call `this.cb.onFrame?.(...)` synchronously; only the Blob branch wraps it in a floating promise with `void` and no catch.
  [read]  :: apps/web/src/lib/ws/client.ts:196 — `ws.binaryType = 'arraybuffer';` is set, so the Blob branch exists specifically as a defensive fallback for hosts that ignore it — i.e. exactly the untested path.

proposed fix: Append `.catch(() => { /* dropped frame — count it */ })` and increment a droppedFrames counter shared with the other binary branches, so a decode failure degrades to a skipped frame rather than an uncaught rejection. Better still, route all three binary branches through one `deliverFrame(bytes)` helper wrapped in try/catch so the error handling is identical whatever the host delivers.
